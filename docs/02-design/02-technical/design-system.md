# Design System — Brand, Tokens, Components, UX Rules

- **อัปเดตล่าสุด:** 2026-08-16
- **อ้างอิงโจทย์:** โจทย์ 1 — ผู้ประกอบการร้านกาแฟต้องการให้ลูกค้าสั่ง Order เองจากที่โต๊ะ
- **อ้างอิง Requirement:** [[../../01-requirements/01-spec/index|01-spec]]
- **แนวทางหลัก:** Earth Tone + Minimalist + MUJI-inspired — เรียบง่าย อบอุ่น ไม่รก ให้ฟังก์ชันนำหน้าความสวยงาม

เอกสารนี้เป็น design system ของ product ร้านกาแฟ self-order ทุก component/pattern ที่ระบุด้านล่าง อ้างอิงกลับไปยัง requirement ที่มีอยู่จริงใน [[../../01-requirements/01-spec/index|01-spec]] — ไม่มี component ใดถูกออกแบบขึ้นลอยๆ โดยไม่มี requirement รองรับ

## 1. Brand Identity & CI

### 1.1 บุคลิกแบรนด์ (Brand Personality)

| ด้าน | นิยาม |
|---|---|
| โทนเสียง (Tone) | อบอุ่น สุภาพ ตรงไปตรงมา ไม่ใช้ศัพท์เทคนิค ไม่ทำให้ลูกค้ารู้สึกว่ากำลังคุยกับ "ระบบ" |
| ค่านิยม (Values) | เรียบง่าย (Simplicity) / จริงใจ (Honesty) / ใส่ใจรายละเอียด (Care in detail) / ยั่งยืน (Quiet, not flashy) |
| สิ่งที่แบรนด์ไม่เป็น | ไม่หรูหราฟุ่มเฟือย ไม่ใช้สีสันจัดจ้าน ไม่ใช้ gimmick/แอนิเมชันเกินจำเป็น ไม่ใช้ pop-up รบกวน |
| แรงบันดาลใจ | MUJI — "ของที่ดีไม่จำเป็นต้องมีโลโก้ใหญ่ๆ" เน้นวัสดุ/พื้นผิวจริง มากกว่าการตกแต่ง |

### 1.2 นัยของแบรนด์ต่อการออกแบบหน้าจอ

เนื่องจากลูกค้าใช้งานระบบเองทั้งหมด (self-order) โดยไม่มีพนักงานคอยอธิบายหน้าจอให้ — บุคลิกแบรนด์ "เรียบง่าย ตรงไปตรงมา" ต้องแปลงเป็นกฎการออกแบบที่เข้มงวด ไม่ใช่แค่ความชอบด้านสุนทรียะ:

- 1 หน้าจอ = 1 การตัดสินใจหลัก (ดูรายละเอียดในหัวข้อ UX Guidelines)
- ไม่มีศัพท์เทคนิคหรือคำย่อในข้อความที่ลูกค้าเห็น (เช่น ใช้ "ส่งออเดอร์แล้ว" ไม่ใช่ "Order submitted successfully")
- ทุก state ของระบบ (กำลังโหลด, ว่าง, ผิดพลาด) ต้องออกแบบไว้ล่วงหน้า ไม่ปล่อยเป็นหน้าขาว/error ดิบของ browser

### 1.3 โลโก้/ตราสัญลักษณ์ (แนวทาง)

โปรเจกต์นี้ยังไม่มีชื่อแบรนด์/โลโก้อย่างเป็นทางการ (เอกสารอ้างว่า "Demo-Project") แนวทางสำหรับเมื่อมีโลโก้จริง:

- **รูปแบบ:** Wordmark เรียบ (ตัวอักษรล้วน) มากกว่า icon/สัญลักษณ์ซับซ้อน — สอดคล้องแนวทาง MUJI ที่ไม่เน้นโลโก้เด่น
- **สี:** ใช้สีเดียว (monochrome) จากโทนสี Text/Ink (ดูหัวข้อ 2.1) บนพื้นหลัง Cream — หลีกเลี่ยงโลโก้หลายสี
- **การใช้งานบน QR code:** ถ้าใส่โลโก้กลาง QR ต้องเป็นเวอร์ชัน monochrome ขนาดเล็ก และต้องผ่านการทดสอบว่าสแกนได้จริงในสภาพแสงร้าน (ไม่ใช่แค่ทดสอบบนจอ)

### 1.4 ภาพถ่าย/ภาพประกอบ (Photography Guidelines)

- แสงธรรมชาติ (natural light) ไม่ใช้แสงสตูดิโอจัดจ้าน
- พื้นผิวจริง: ไม้ ดิน เซรามิกดิบ ผ้าลินิน — หลีกเลี่ยงพลาสติกมันวาว
- ไม่ครอบ filter สีจัด ให้คงโทนสีธรรมชาติของอาหาร/เครื่องดื่มจริง
- เมนูที่ยังไม่มีรูปถ่ายจริง ให้ใช้ placeholder สีพื้น (จากโทนสี Sand/Clay) พร้อมชื่อเมนู แทนการใช้รูป stock/AI ที่ดูไม่ตรงกับสินค้าจริง

## 2. Design Tokens / Design System

### 2.1 Colors

พื้นฐานของโทนสีคือ **neutral earth tone เป็นหลัก (~90% ของพื้นที่หน้าจอ) และใช้สี accent เพียงจุดเดียวต่อหน้าจอ** เพื่อคงความรู้สึกเรียบสงบแบบ MUJI — สีสันไม่ใช่ตัวดึงความสนใจ แต่ typography/spacing/hierarchy ทำหน้าที่นั้นแทน

#### Neutral / Base (พื้นหลัง, พื้นผิว, เส้นขอบ)

```
--color-cream-50:   #FAF8F4   /* พื้นหลังหลักของแอป */
--color-cream-100:  #F5F1E9   /* พื้นหลัง section รอง */
--color-cream-200:  #EDE6D8   /* พื้นผิว card ที่ไม่ active */
--color-sand-300:   #DFD4BE   /* เส้นขอบ, divider */
--color-sand-400:   #C9BA9C   /* เส้นขอบเข้มขึ้น (input border) */
```

#### Ink / Text (ข้อความ)

```
--color-ink-900:    #2E2620   /* หัวข้อ, ข้อความสำคัญ */
--color-ink-700:    #55483C   /* ข้อความเนื้อหาปกติ */
--color-ink-500:    #83766A   /* ข้อความรอง (secondary, timestamp) */
--color-ink-300:    #B0A497   /* placeholder, disabled text */
```

> หมายเหตุ: ไม่ใช้สีดำสนิท (`#000000`) หรือขาวสนิท (`#FFFFFF`) เลยในระบบ — โทนดินอบอุ่นทุกระดับ (รวมถึงพื้นหลัง "ขาว" และตัวหนังสือ "ดำ") เพื่อคงบุคลิก earth tone ไว้แม้ในรายละเอียดที่เล็กที่สุด

#### Primary — Coffee Brown (ปุ่มหลัก, CTA)

```
--color-coffee-700:  #6B4E3D   /* ปุ่มหลัก, active state */
--color-coffee-800:  #543C2F   /* hover/pressed state ของปุ่มหลัก */
--color-coffee-100:  #EAE0D8   /* พื้นหลังอ่อนของ badge/tag ที่เกี่ยวกับ coffee */
```

#### Accent — Clay / Terracotta (จุดเน้นรอง, badge สถานะ "กำลังทำ")

```
--color-clay-600:   #B37752
--color-clay-100:   #F1E2D3
```

#### Accent — Sage Green (สถานะสำเร็จ, การยืนยัน)

```
--color-sage-600:   #6E7C5A
--color-sage-100:   #E4E8DA
```

ใช้เฉพาะกับสถานะ "เสร็จ/เสิร์ฟแล้ว" (อ้างอิง [[../../01-requirements/01-spec/20260815-01-kitchen-notification-order-handling|20260815-01-kitchen-notification-order-handling]]) — ไม่ใช้สีเขียวจัดแบบ "success" ทั่วไปของ UI framework เพราะจะขัดกับโทน earth tone

#### Semantic — Warning/Error (ใช้อย่างประหยัด)

```
--color-rust-600:   #A6543C   /* ข้อความ error, ปุ่ม "ลองส่งใหม่" */
--color-rust-100:   #F2E0D8   /* พื้นหลัง error banner */
```

หลีกเลี่ยงสีแดงสด (`#FF0000` เป็นต้น) — ใช้สี rust/terracotta เข้มแทน เพื่อให้ข้อความ error ยังคง "อยู่ในโทน" ของแบรนด์ ไม่ทำลาย visual language ทั้งหน้าจอ แม้ในสถานการณ์ผิดพลาด

#### กฎการใช้สี (Color Usage Rules)

1. พื้นหลังหน้าจอ = `cream-50` เสมอ ไม่มีข้อยกเว้น
2. สี accent (clay, sage, rust) ใช้ได้แค่ **จุดเดียวที่สำคัญที่สุดของหน้าจอนั้น** เช่น badge สถานะออเดอร์ 1 อัน ไม่ใช่หลายจุดพร้อมกัน
3. ห้ามใช้ gradient หรือสีไล่เฉด — MUJI aesthetic คือสีทึบ (solid/flat) เท่านั้น
4. Contrast ratio ของข้อความต่อพื้นหลังต้องผ่าน WCAG AA ขั้นต่ำ (4.5:1 สำหรับ body text) แม้จะใช้โทนสีอ่อน — ห้ามลดทอน accessibility เพื่อความสวยงาม

### 2.2 Typography

```
--font-thai:     "Noto Sans Thai", sans-serif      /* ข้อความภาษาไทยทั้งหมด (เมนูเริ่มต้นรองรับไทยอย่างเดียวตาม open question ของสเปก) */
--font-latin:    "Inter", sans-serif               /* ตัวเลข, ราคา, timestamp, ภาษาอังกฤษ */
```

เลือก sans-serif เรียบ ไม่มี serif เพื่อความรู้สึก "ทันสมัยแบบเรียบ" — หลีกเลี่ยงฟอนต์ display/ฟอนต์ตกแต่งในทุกจุดที่ลูกค้าต้องอ่านเพื่อสั่งอาหาร (เมนู, ราคา, ปุ่ม)

#### Type Scale

| Token | ขนาด | น้ำหนัก | ใช้กับ |
|---|---|---|---|
| `--text-display` | 28px / 1.3 | Semibold (600) | ชื่อหมวดหมู่เมนู, หัวข้อหน้า |
| `--text-title` | 20px / 1.4 | Semibold (600) | ชื่อเมนู, หัวข้อการ์ด |
| `--text-body` | 16px / 1.5 | Regular (400) | เนื้อหาทั่วไป, คำอธิบายเมนู |
| `--text-price` | 16px / 1.4 | Semibold (600) | ราคา — ให้น้ำหนักเท่าชื่อเมนูเสมอ ไม่ใช่ตัวเลขเล็กจ้อย |
| `--text-caption` | 13px / 1.4 | Regular (400) | timestamp, หมายเลขโต๊ะ, ข้อความรอง |
| `--text-button` | 16px / 1.2 | Medium (500) | ข้อความบนปุ่ม |

กฎ: **ไม่เกิน 3 ระดับน้ำหนักฟอนต์ต่อหน้าจอเดียว** (เช่น Semibold สำหรับหัวข้อ, Regular สำหรับเนื้อหา, Medium สำหรับปุ่ม) เพื่อลดความรกทางสายตา

### 2.3 Spacing

ใช้ scale ฐาน 4px แบบ MUJI ที่เน้นช่องว่างมากกว่าปกติ (generous whitespace):

```
--space-1:   4px
--space-2:   8px
--space-3:   12px
--space-4:   16px   /* ค่ามาตรฐานระหว่าง element ทั่วไป */
--space-6:   24px   /* padding ภายใน card */
--space-8:   32px   /* ระยะห่างระหว่าง section */
--space-12:  48px   /* margin บน/ล่างของหน้าจอหลัก */
```

กฎ: padding ภายใน touch target (ปุ่ม, การ์ดเมนูที่กดได้) ต้องไม่ต่ำกว่า `--space-3` (12px) ทุกด้าน และพื้นที่กดขั้นต่ำ **44×44px** เสมอ (มาตรฐาน mobile accessibility เนื่องจากลูกค้าใช้งานผ่านมือถือของตัวเองเป็นหลัก)

### 2.4 Radius & Elevation

```
--radius-sm:   4px    /* input, badge */
--radius-md:   8px    /* button, card เมนู */
--radius-lg:   16px   /* modal, bottom sheet (หน้าสรุปออเดอร์) */
```

MUJI aesthetic หลีกเลี่ยงเงา (shadow) หนักๆ — ใช้ **เส้นขอบบาง (`1px solid var(--color-sand-300)`) แทน drop shadow** เป็นค่าเริ่มต้นสำหรับแยก card ออกจากพื้นหลัง shadow ใช้เฉพาะ element ที่ลอยเหนือเนื้อหาจริงๆ (เช่น bottom sheet สรุปออเดอร์, modal ยืนยัน) และต้องเป็นเงาที่นุ่ม/จางมาก:

```
--shadow-float: 0 2px 12px rgba(46, 38, 32, 0.08)
```

## 3. UI Components & Patterns

ทุก component อ้างอิง requirement ต้นทางกำกับไว้ในวงเล็บ

### 3.1 Menu Card (การ์ดเมนู)
อ้างอิง: [[../../01-requirements/01-spec/20260802-01-table-qr-self-order|20260802-01-table-qr-self-order]], [[../../01-requirements/01-spec/20260816-03-back-office-menu-price-crud|20260816-03-back-office-menu-price-crud]]

- โครงสร้าง: รูป/placeholder สี → ชื่อเมนู (`--text-title`) → ราคา (`--text-price`) → ปุ่ม "+" เพิ่มลงตะกร้า
- พื้นหลัง `cream-100`, ขอบ `1px solid sand-300`, radius `--radius-md`
- **State "หมดชั่วคราว"** (จาก flag เปิด/ปิดขายใน `20260815-01`): ลด opacity ของรูป/ข้อความเหลือ ~50%, ปุ่ม "+" ถูกแทนที่ด้วย label ข้อความ "หมดชั่วคราว" สี `ink-500` — **ห้ามซ่อนการ์ดออกไปเลย** เพราะลูกค้าควรรู้ว่าเมนูนี้มีอยู่แต่หมดชั่วคราว ไม่ใช่ไม่มีเมนูนี้ในร้าน

### 3.2 Order Status Badge (badge สถานะออเดอร์)
อ้างอิง: [[../../01-requirements/01-spec/20260815-01-kitchen-notification-order-handling|20260815-01-kitchen-notification-order-handling]], [[../../01-requirements/01-spec/20260816-01-order-status-notification-to-customer|20260816-01-order-status-notification-to-customer]]

3 สถานะ ต้องแยกกันด้วยสีที่จำเขาซ้ำได้ทันทีโดยไม่ต้องอ่านข้อความ (แต่ข้อความต้องอยู่เสมอ ไม่ใช้สีอย่างเดียว เพื่อ accessibility):

| สถานะ | สี badge | พื้นหลัง |
|---|---|---|
| ส่งแล้ว (รอครัวรับทราบ) | `ink-500` | `cream-200` |
| ครัวรับทราบแล้ว (กำลังทำ) | `clay-600` | `clay-100` |
| เสร็จ/เสิร์ฟแล้ว | `sage-600` | `sage-100` |

บนหน้าจอลูกค้า badge นี้ต้องอัปเดตแบบ real-time โดยไม่ต้องกดรีเฟรช (ตาม `20260816-01`) — เมื่อสถานะเปลี่ยน ให้มี transition สีแบบ fade (200ms) ไม่ใช่เปลี่ยนทันทีแบบกระตุก เพื่อให้ลูกค้าสังเกตเห็นการเปลี่ยนแปลงแต่ไม่รู้สึกกระตุกตา

### 3.3 Order Summary Sheet (หน้าสรุปออเดอร์ก่อนยืนยัน — 2-step confirm)
อ้างอิง: [[../../01-requirements/01-spec/20260802-01-table-qr-self-order|20260802-01-table-qr-self-order]]

- แสดงเป็น bottom sheet (`--radius-lg`, `--shadow-float`) ไม่ใช่หน้าใหม่เต็มจอ — ลูกค้าควรรู้สึกว่ายังอยู่ในบริบทเดิม
- รายการ: ชื่อเมนู × จำนวน → ราคารวมต่อรายการ → เส้นคั่น → ยอดรวมทั้งหมด (`--text-display`, น้ำหนักเด่นที่สุดในหน้าจอ)
- ปุ่มหลัก "ยืนยันออเดอร์" (`coffee-700`) เต็มความกว้าง อยู่ล่างสุด ตรึงตำแหน่ง (sticky) เสมอแม้ scroll รายการยาว
- ปุ่มรอง "แก้ไขรายการ" เป็น text button ไม่มีพื้นหลัง วางเหนือปุ่มหลัก ไม่ใช่ข้างๆ กัน (ป้องกันการกดผิดโดยไม่ตั้งใจในขั้นตอนสำคัญที่สุดของ flow)

### 3.4 Error Banner + Retry (แจ้ง error ตอนส่งออเดอร์ไม่สำเร็จ)
อ้างอิง: [[../../01-requirements/01-spec/20260815-01-kitchen-notification-order-handling|20260815-01-kitchen-notification-order-handling]]

- แสดงเป็น banner คงที่ด้านบนของปุ่มยืนยัน (ไม่ใช่ toast ที่หายไปเอง) พื้นหลัง `rust-100` ขอบ `1px solid rust-600` ข้อความ `ink-900`
- ข้อความต้องระบุสาเหตุแบบเข้าใจง่าย + ปุ่ม "ลองส่งใหม่" (`rust-600`, outline style ไม่ใช่ filled เพื่อไม่แข่งกับปุ่มยืนยันหลัก)
- **กฎเข้ม:** ห้ามแสดงสถานะ "ส่งสำเร็จ" ใดๆ (ไม่ว่าจะเป็น badge, ข้อความ, หรือ animation) จนกว่าจะได้รับการยืนยันจาก backend จริง — ไม่มี optimistic UI ในจุดนี้โดยเด็ดขาด

### 3.5 Kitchen/Bar Slip Ticket (สลิปพิมพ์ในครัว)
อ้างอิง: [[../../01-requirements/01-spec/20260815-01-kitchen-notification-order-handling|20260815-01-kitchen-notification-order-handling]]

แม้เป็นสิ่งพิมพ์ (ไม่ใช่ digital UI) แต่ต้องออกแบบ layout ตาม typography scale เดียวกัน เพื่อความสอดคล้อง:
- หมายเลขโต๊ะ: ใหญ่ที่สุดบนสลิป อยู่บนสุด (พนักงานต้องเห็นก่อนอย่างอื่น)
- เวลา → รายการอาหาร/เครื่องดื่ม (แต่ละรายการ font ชัดเจน ไม่ใช้ font ตกแต่ง เพราะพิมพ์ด้วยเครื่องพิมพ์ความร้อน)
- ใช้ตัวหนา (bold) ล้วน ไม่ใช้สี (เครื่องพิมพ์ส่วนใหญ่เป็นขาวดำ)

### 3.6 Back-office Form (จัดการเมนู/ราคา)
อ้างอิง: [[../../01-requirements/01-spec/20260816-03-back-office-menu-price-crud|20260816-03-back-office-menu-price-crud]]

- ใช้ style เดียวกับฝั่งลูกค้า (สี, spacing, typography) — back-office ไม่ใช่ "ระบบคนละชุด" ที่ดูต่างไปเป็น dashboard สีฉูดฉาดแบบ SaaS ทั่วไป เพื่อความสอดคล้องของแบรนด์แม้ฝั่งพนักงาน
- Input field: ขอบ `1px solid sand-400`, radius `--radius-sm`, พื้นหลัง `cream-50`, focus state เปลี่ยนขอบเป็น `coffee-700`
- ปุ่ม "ลบเมนู" ต้องเป็นปุ่ม outline สี `rust-600` พร้อม confirm dialog เสมอ (การลบเป็น permanent action ตาม scope ของสเปก แยกจาก flag เปิด/ปิดขายชั่วคราวซึ่งไม่ต้อง confirm)

### 3.7 Payment QR Screen (เคาน์เตอร์)
อ้างอิง: [[../../01-requirements/01-spec/20260816-02-counter-qr-payment|20260816-02-counter-qr-payment]]

- หน้าจอสำหรับพนักงานเคาน์เตอร์ (ไม่ใช่ลูกค้า) — แสดงยอดรวม (`--text-display`) กลางจอ, QR code ขนาดใหญ่อยู่ตรงกลาง, พื้นหลัง `cream-50` ล้วนไม่มีสิ่งรบกวนสายตา (ลูกค้าต้องสแกนจากหน้าจอนี้)
- สถานะรอชำระ/ชำระสำเร็จ ใช้ badge เดียวกับ pattern ในหัวข้อ 3.2 (`ink-500` → `sage-600`) เพื่อความสอดคล้องทั้งระบบ

## 4. UX Guidelines & Rules

หลักการเหล่านี้มีผลเหนือกว่าความชอบด้าน visual — ถ้า decision ใดขัดกับหลักการข้อใดข้อหนึ่งด้านล่าง ให้ยึดหลักการนี้ก่อนความสวยงาม

### 4.1 หลักการหลัก (Core Principles)

1. **หนึ่งหน้าจอ หนึ่งการตัดสินใจหลัก** — อย่าให้ลูกค้าต้องเลือกหลายอย่างพร้อมกันในหน้าเดียว (เช่น หน้าดูเมนูไม่ควรมีปุ่มเรียกพนักงาน/ปุ่มเรียกบิลปนอยู่ ให้แยกเป็นคนละจุดชัดเจน)
2. **ไม่มีขั้นตอน "เรียกพนักงาน" ใน flow หลัก** — ตรงกับกฎของ user-journey-writer และโจทย์ 1 โดยตรง (ดู [[01-prototypes/user-journey-self-order|user-journey-self-order]]) ทุก UI ที่ออกแบบต้องเช็คว่าไม่มีจุดใดบังคับให้ลูกค้าต้องเรียกพนักงานเพื่อดำเนิน flow การสั่งอาหารต่อ (ยกเว้น exception path ที่ระบุไว้ชัดเจนแล้วในสเปก เช่น การแก้ไขออเดอร์หลังครัวรับทราบแล้ว)
3. **ไม่มี false positive ของสถานะ** — ห้ามแสดงว่าสำเร็จก่อนได้รับการยืนยันจาก backend จริง (ดูหัวข้อ 3.4) ใช้กับทุก action ที่ irreversible เช่น การส่งออเดอร์, การชำระเงิน
4. **Whitespace คือฟีเจอร์ ไม่ใช่พื้นที่ว่างที่ต้องเติม** — ห้าม "อัด" ข้อมูล/ปุ่มเพิ่มเพื่อใช้พื้นที่ให้เต็ม ถ้าหน้าจอดูโล่ง แปลว่าออกแบบถูกทางแล้วสำหรับแนวทาง MUJI
5. **Real-time > ต้องกดรีเฟรชเอง** — ทุกจุดที่สถานะเปลี่ยนได้ (ออเดอร์, เมนูหมดชั่วคราว, การชำระเงิน) ต้องอัปเดตให้ลูกค้า/พนักงานเห็นโดยไม่ต้องกดรีเฟรชเอง (ตามที่ยืนยันไว้ใน `20260816-01`)

### 4.2 Accessibility

- Contrast ratio ขั้นต่ำ WCAG AA (4.5:1 สำหรับ body text, 3:1 สำหรับ large text/UI component)
- ห้ามสื่อความหมายด้วยสีอย่างเดียว (color-only signaling) — badge สถานะทุกอันต้องมีข้อความกำกับเสมอ ไม่ใช่แค่จุดสี
- ขนาดตัวอักษรขั้นต่ำบนหน้าจอลูกค้า 16px (`--text-body`) เพราะใช้งานผ่านมือถือของลูกค้าเองในสภาพแสงร้าน/แสงแดดที่หลากหลาย
- พื้นที่กดขั้นต่ำ 44×44px ทุกปุ่ม/การ์ดที่กดได้ (ดูหัวข้อ 2.3)

### 4.3 ภาษา (Language)

- ภาษาเริ่มต้นของระบบคือ**ภาษาไทยเท่านั้น** (ตาม open question ของ [[../../01-requirements/01-spec/20260802-01-table-qr-self-order|20260802-01-table-qr-self-order]] ที่ยังไม่ยืนยัน multi-language) — ห้ามออกแบบ UI ที่ผูกกับสมมติฐานว่ามีหลายภาษาจนกว่าจะมี requirement ยืนยันเรื่องนี้อย่างเป็นทางการ
- ข้อความในระบบใช้ภาษาพูดปกติ ไม่ใช้คำทับศัพท์ภาษาอังกฤษที่ไม่จำเป็น (เช่น "ยืนยันออเดอร์" ไม่ใช่ "Confirm Order")

### 4.4 Error & Empty States

ทุก component ต้องมีอย่างน้อย 3 state ที่ออกแบบไว้ล่วงหน้าเสมอ (ไม่ปล่อยเป็นค่า default ของ framework):
1. **Loading** — ใช้ skeleton screen โทนสี `cream-200` (ไม่ใช้ spinner หมุนตลอดเวลา เพราะรู้สึกไม่นิ่ง ขัดกับความรู้สึก "สงบ" ของแบรนด์)
2. **Empty** — เช่น ตะกร้ายังไม่มีรายการ ให้ใช้ข้อความสั้น + ไอคอนเรียบสีเดียว ไม่ใช้ illustration สีสันจัด
3. **Error** — ตามรูปแบบหัวข้อ 3.4 เสมอ ไม่แสดง error code ดิบของระบบให้ลูกค้าเห็น (เช่น "500 Internal Server Error") ให้แปลเป็นภาษาที่ลูกค้าเข้าใจ

### 4.5 ความสอดคล้องระหว่างฝั่งลูกค้าและฝั่งพนักงาน

ทุกหน้าจอ (ลูกค้า, ครัว/บาร์, เคาน์เตอร์, back-office) ใช้ token ชุดเดียวกันทั้งหมดในเอกสารนี้ — ไม่มีชุดสี/font แยกสำหรับ "ฝั่ง admin" เพื่อคงเอกลักษณ์แบรนด์เดียวกันตลอดทั้ง product แม้ผู้ใช้งานจะเป็นคนละกลุ่ม (ลูกค้า vs พนักงาน)
