## รายละเอียด Feature

### 1. ลูกค้าสั่งอาหาร/เครื่องดื่มเองผ่านการสแกน QR code ที่โต๊ะ

- **MoSCoW:** Must — เหตุผล: เป็น core flow ที่ตอบโจทย์ 1 โดยตรง (แทนที่การเรียกพนักงานรับออเดอร์) `backlog.md` กำหนด priority "สูง" สำหรับส่วนนี้ และถ้าไม่มีฟีเจอร์นี้ก็ไม่มี self-order เลย
- **Requirement อ้างอิง:** [[01-spec/20260802-01-table-qr-self-order|ลูกค้าสั่งอาหาร/เครื่องดื่มเองผ่านการสแกน QR code ที่โต๊ะ]]
- **คำอธิบาย:** ลูกค้าสแกน QR ที่ผูกกับหมายเลขโต๊ะ เปิดดูเมนูบนมือถือของตัวเอง เลือกรายการใส่ตะกร้า ตรวจสอบที่หน้าสรุปแบบ 2-step confirm แล้วระบบส่งออเดอร์เข้าครัว/บาร์อัตโนมัติโดยไม่ผ่านพนักงาน
- **User Story ที่เกี่ยวข้อง:** สแกน QR ดูเมนู, เลือกรายการใส่ตะกร้า, เห็นหน้าสรุปก่อนยืนยัน, ระบบส่งเข้าครัว/บาร์อัตโนมัติหลังยืนยัน

### 2. การแจ้งเตือนครัว/บาร์ด้วยสลิปพิมพ์อัตโนมัติ และสถานะออเดอร์

- **MoSCoW:** Must — เหตุผล: baseline ของเอกสารต้นทางคือ "สูง" และเนื้อหา feature นี้คือการเติมเต็มช่องว่างที่วิกฤตที่สุดของ self-order flow เดิม — สเปกเดิม (`20260802-01-table-qr-self-order`) ระบุแค่ "ส่งเข้าครัว/บาร์อัตโนมัติ" โดยไม่เคยนิยามกลไกฝั่งรับเลย ถ้าไม่มี feature นี้ ออเดอร์ที่ลูกค้ายืนยันแล้วจะไม่มีทางไปถึงครัว/บาร์ได้จริง ทำให้ core self-order flow ใช้งานจริงไม่ได้ทั้งหมด จึงต้องเป็น Must
- **Requirement อ้างอิง:** [[01-spec/20260815-01-kitchen-notification-order-handling#Business Rules / เงื่อนไข|การแจ้งเตือนครัว/บาร์ และสถานะออเดอร์]]
- **คำอธิบาย:** เมื่อลูกค้ายืนยันออเดอร์สำเร็จ (2-step confirm) ระบบพิมพ์สลิปออกที่เครื่องพิมพ์ในครัว/บาร์ทันที (ระบุหมายเลขโต๊ะ, เวลา, รายการที่สั่ง) พร้อมติดตามสถานะออเดอร์อย่างน้อย 3 ระดับ: "ส่งแล้ว (รอครัวรับทราบ)" → "ครัวรับทราบแล้ว (กำลังทำ)" → "เสร็จ/เสิร์ฟแล้ว" โดยพนักงานครัวกดรับทราบเพื่อล็อกออเดอร์ไม่ให้ลูกค้าแก้ไขต่อ
- **User Story ที่เกี่ยวข้อง:** พนักงานครัว/บาร์ต้องการสลิปพิมพ์ออกอัตโนมัติทันทีที่มีออเดอร์ใหม่, พนักงานครัว/บาร์ต้องการกดรับทราบออเดอร์เพื่อล็อกไม่ให้ลูกค้าแก้ไขอีก
- **หมายเหตุ:** รวมกฎ "reset ตะกร้าเก่าอัตโนมัติหลังออเดอร์ก่อนหน้า mark ว่าเสร็จ/เสิร์ฟแล้ว" ไว้ใน feature นี้ด้วย เพราะเป็นกลไกที่ผูกกับการเปลี่ยนสถานะออเดอร์โดยตรง ไม่แยกเป็น feature ต่างหาก — กฎนี้ระบุไว้ในสเปกต้นทางว่าเป็นสมมติฐาน (assumption) ยังไม่ยืนยันกับผู้ใช้ 100%

### 3. การเก็บรักษาและลบ/anonymize order log ตาม PDPA (retention 90 วัน)

- **MoSCoW:** Should — เหตุผล: `backlog.md` ระบุไว้ชัดเจนว่าส่วนนี้ priority "กลาง" แยกจากส่วนหลัก แม้เป็นเงื่อนไขด้าน compliance/ความปลอดภัยข้อมูลที่สำคัญ แต่ไม่ได้ block การสั่งอาหารของลูกค้าโดยตรง (ระบบสั่งอาหารทำงานได้แม้ auto-delete job ยังไม่เสร็จ) จึงไม่ใช่ Must
- **Requirement อ้างอิง:** [[01-spec/20260802-01-table-qr-self-order#Business Rules / เงื่อนไข|การเก็บ log ออเดอร์และการปฏิบัติตาม PDPA]]
- **คำอธิบาย:** เก็บ order log เฉพาะเลขโต๊ะ + เวลา + รายการอาหาร (ไม่เก็บข้อมูลที่ระบุตัวตนได้) เป็นเวลา 90 วัน จากนั้นต้องลบ/anonymize อัตโนมัติ พร้อมจำกัดสิทธิ์เข้าถึง log เฉพาะเจ้าของร้าน/พนักงานที่ได้รับอนุญาต
- **User Story ที่เกี่ยวข้อง:** ไม่มี user story ของลูกค้าโดยตรง — เป็น business rule ฝั่ง backend/compliance
- **หมายเหตุ:** เป็น non-functional requirement ด้าน compliance ไม่ใช่สิ่งที่ลูกค้าโต้ตอบด้วยตรงๆ แต่แยกเป็น feature ต่างหากเพื่อ track การ implement auto-delete/anonymize job ให้ชัดเจนแยกจาก core ordering flow

### 4. การแก้ไข/ยกเลิกออเดอร์โดยลูกค้าก่อนครัวรับทราบ

- **MoSCoW:** Should — เหตุผล: baseline ของเอกสารต้นทางคือ "สูง" แต่เนื้อหาสเปกระบุชัดว่า feature นี้ทำงานได้เฉพาะช่วงที่ออเดอร์ยังอยู่ในสถานะ "ส่งแล้ว (รอครัวรับทราบ)" เท่านั้น และเมื่อพ้นช่วงนี้ไปแล้วมี exception path (เรียกพนักงานเป็นกรณีพิเศษ) รองรับอยู่แล้ว — core self-order flow ยังคงทำงานได้สมบูรณ์แม้ไม่มี feature นี้ (ลูกค้าเพียงต้องเรียกพนักงานกรณีสั่งผิด) จึงลดจาก Must เป็น Should
- **Requirement อ้างอิง:** [[01-spec/20260815-01-kitchen-notification-order-handling#Business Rules / เงื่อนไข|การแก้ไข/ยกเลิกออเดอร์โดยลูกค้า]]
- **คำอธิบาย:** ลูกค้าสามารถยกเลิกหรือแก้ไขออเดอร์ที่เพิ่งยืนยันไปได้ด้วยตัวเอง ตราบใดที่ครัวยังไม่กดรับทราบออเดอร์นั้น เมื่อครัวรับทราบแล้วออเดอร์จะถูกล็อก ลูกค้าที่ต้องการเปลี่ยนแปลงหลังจากนั้นต้องเรียกพนักงานเป็นกรณีพิเศษ
- **User Story ที่เกี่ยวข้อง:** ลูกค้าต้องการยกเลิก/แก้ไขออเดอร์ที่เพิ่งยืนยันไปได้ด้วยตัวเอง ตราบใดที่ครัวยังไม่เริ่มทำ

### 5. การเปิด/ปิดขายเมนูรายการชั่วคราว

- **MoSCoW:** Should — เหตุผล: baseline ของเอกสารต้นทางคือ "สูง" แต่สเปกระบุชัดว่านี่คือ "flag เปิด/ปิดแบบง่าย ไม่ใช่ real-time inventory" และ scope ของเอกสารเองระบุว่าระบบจัดการเมนู/สต๊อกแบบเต็มรูปแบบถูกยกไปเป็น requirement แยกในอนาคต แสดงว่า feature นี้เป็นกลไก stopgap ไม่ใช่ critical path ของการสั่งอาหารหลัก (ลูกค้ายังสั่งเมนูอื่นได้ปกติแม้ไม่มี feature นี้ เพียงมีความเสี่ยงสั่งรายการที่ของหมด) จึงลดจาก Must เป็น Should
- **Requirement อ้างอิง:** [[01-spec/20260815-01-kitchen-notification-order-handling#Business Rules / เงื่อนไข|การเปิด/ปิดขายเมนู]]
- **คำอธิบาย:** พนักงานกดปิดขายเมนูรายการใดรายการหนึ่งแบบชั่วคราวเมื่อของหมด ระบบจะแสดงข้อความ "หมดชั่วคราว" ให้ลูกค้าเห็นทันทีบนเมนู เพื่อป้องกันลูกค้าสั่งรายการที่ทำไม่ได้
- **User Story ที่เกี่ยวข้อง:** พนักงานต้องการกดปิดขายเมนูรายการที่ของหมดชั่วคราว เพื่อไม่ให้ลูกค้าสั่งรายการที่ทำไม่ได้, ลูกค้าต้องการเห็นข้อความ "หมดชั่วคราว" บนเมนูที่ปิดขาย เพื่อไม่เลือกรายการนั้น

### 6. การแจ้ง error และลองส่งออเดอร์ใหม่เมื่อส่งไม่สำเร็จ

- **MoSCoW:** Should — เหตุผล: baseline ของเอกสารต้นทางคือ "สูง" แต่ในสเปกเองระบุไว้ใน Open Questions ว่ารายละเอียดของ error handling นี้เป็นสมมติฐาน (assumption) ที่ยังไม่ยืนยันกับผู้ใช้ 100% และเป็นการจัดการ edge case (เน็ตหลุด/ระบบล่ม) ไม่ใช่ flow หลักที่เกิดขึ้นทุกครั้ง อย่างไรก็ตามยังคงสำคัญต่อความน่าเชื่อถือของ core self-order flow (ป้องกันลูกค้าเข้าใจผิดว่าออเดอร์สำเร็จทั้งที่ยังไม่ถึงครัว) จึงคงไว้ที่ Should ไม่ลดถึง Could
- **Requirement อ้างอิง:** [[01-spec/20260815-01-kitchen-notification-order-handling#Business Rules / เงื่อนไข|Error handling]]
- **คำอธิบาย:** เมื่อส่งออเดอร์ไม่สำเร็จ (เน็ตหลุด/ระบบล่ม) ระบบแสดง error message ที่ชัดเจนพร้อมปุ่มลองส่งใหม่ ห้ามแสดงว่าออเดอร์สำเร็จถ้ายังไม่ได้รับการยืนยันจาก backend
- **User Story ที่เกี่ยวข้อง:** ลูกค้าเมื่อส่งออเดอร์ไม่สำเร็จ (เน็ตหลุด/ระบบล่ม) ต้องการเห็น error message ชัดเจนพร้อมปุ่มลองส่งใหม่ เพื่อไม่เข้าใจผิดว่าออเดอร์สำเร็จแล้วทั้งที่ยังไม่ถึงครัว
- **หมายเหตุ:** เป็นสมมติฐานตามที่ระบุใน Open Questions ของสเปกต้นทาง ยังไม่ยืนยันรายละเอียดกับผู้ใช้จริง

### 7. การสั่งพร้อมกันหลายเครื่องที่โต๊ะเดียวกัน (รวมบิลเดียว)

- **MoSCoW:** Could — เหตุผล: baseline ของเอกสารต้นทางคือ "สูง" แต่เนื้อหาสเปกระบุ feature นี้ไว้เป็นเพียง business rule บรรทัดเดียวที่ระบุชัดว่าเป็นสมมติฐาน (สมมติฐาน) โดยไม่มี user story ของตัวเองรองรับ และเป็น edge case ที่ไม่ใช่เงื่อนไขจำเป็นต่อ MVP ของ self-order (แต่ละโต๊ะเริ่มต้นด้วยลูกค้าคนเดียวสั่งจากเครื่องเดียวก็ใช้งาน core flow ได้ปกติ) จึงลดจาก Must/Should เหลือ Could
- **Requirement อ้างอิง:** [[01-spec/20260815-01-kitchen-notification-order-handling#Business Rules / เงื่อนไข|การสั่งพร้อมกันหลายเครื่องที่โต๊ะเดียวกัน]]
- **คำอธิบาย:** เมื่อมีลูกค้าหลายคนที่โต๊ะเดียวกันสั่งอาหารจากคนละเครื่อง (สแกน QR โต๊ะเดียวกันคนละมือถือ) ระบบรวมออเดอร์เป็นตะกร้า/บิลเดียวกันของโต๊ะนั้น
- **User Story ที่เกี่ยวข้อง:** ไม่มี user story ตรงในสเปกต้นทาง — เป็น business rule ที่ตั้งไว้เป็นสมมติฐาน
- **หมายเหตุ:** เป็นสมมติฐานตามที่ระบุใน Open Questions ของสเปกต้นทาง ยังไม่ยืนยันรายละเอียดกับผู้ใช้จริง (เช่น กรณีขัดแย้งกันเรื่องการแก้ไข/ยกเลิกออเดอร์ระหว่างเครื่องต่างๆ ที่โต๊ะเดียวกัน ยังไม่ได้นิยาม)
