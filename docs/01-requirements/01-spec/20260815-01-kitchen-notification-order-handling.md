# การแจ้งเตือนครัว/บาร์ และการจัดการออเดอร์หลังยืนยัน (เติมเต็มช่องว่างของ self-order flow)

- **วันที่สร้าง:** 2026-08-15
- **อ้างอิงโจทย์:** โจทย์ 1 — ผู้ประกอบการร้านกาแฟต้องการให้ลูกค้าสั่ง Order เองจากที่โต๊ะ
- **สถานะ:** Draft
- **เอกสารที่เกี่ยวข้อง:** [[01-spec/20260802-01-table-qr-self-order|20260802-01-table-qr-self-order]] (ต่อยอด/เติมเต็ม flow เดิม แต่แยกเอกสาร)

## ความต้องการ (Requirement)
จากการรีวิว feature list/user journey ของ self-order flow เดิม (`20260802-01-table-qr-self-order`) พบว่ามีช่องว่างสำคัญหลายจุดที่ทำให้ flow ยังใช้งานไม่ได้จริงครบวงจร โดยเฉพาะ **ไม่มีกลไกใดๆ ที่ทำให้ครัว/บาร์รู้ว่ามีออเดอร์ใหม่เข้ามา** (สเปกเดิมระบุแค่ "ส่งเข้าครัว/บาร์อัตโนมัติ" แต่ไม่เคยนิยามกลไกฝั่งรับ) รวมถึงไม่มีการจัดการกรณี edge case ที่จำเป็นต่อการใช้งานจริง เช่น การแก้ไข/ยกเลิกออเดอร์หลังยืนยัน, สินค้าหมดระหว่างลูกค้าเลือกเมนู, การสั่งพร้อมกันหลายเครื่องที่โต๊ะเดียวกัน, error handling เมื่อส่งออเดอร์ไม่สำเร็จ, และการ reset ตะกร้าเก่าของโต๊ะ

เอกสารนี้เติมเต็มช่องว่างเหล่านี้ เพื่อให้ self-order flow ทำงานจบในตัวได้จริงตั้งแต่ลูกค้าสั่งจนถึงครัวรับออเดอร์ โดยไม่ต้องมีขั้นตอน "เรียกพนักงานมารับออเดอร์" ในกรณีปกติ (สอดคล้องกับโจทย์ 1)

## User Stories
- ในฐานะพนักงานครัว/บาร์ ฉันต้องการให้มีสลิปพิมพ์ออกมาอัตโนมัติทันทีที่มีออเดอร์ใหม่ เพื่อให้รู้ว่าต้องทำอะไรให้โต๊ะไหน โดยไม่ต้องคอยเช็คหน้าจอเอง
- ในฐานะลูกค้า ฉันต้องการยกเลิก/แก้ไขออเดอร์ที่เพิ่งยืนยันไปได้ด้วยตัวเอง ตราบใดที่ครัวยังไม่เริ่มทำ เพื่อแก้ไขความผิดพลาดโดยไม่ต้องเรียกพนักงาน
- ในฐานะพนักงานครัว/บาร์ ฉันต้องการกดรับทราบออเดอร์ (เช่น กดปุ่มที่ POS หรือขีดสลิป) เพื่อให้ระบบล็อกออเดอร์นั้นไม่ให้ลูกค้าแก้ไขอีกเมื่อเริ่มทำแล้ว
- ในฐานะพนักงาน ฉันต้องการกดปิดขายเมนูรายการที่ของหมดชั่วคราว เพื่อไม่ให้ลูกค้าสั่งรายการที่ทำไม่ได้
- ในฐานะลูกค้า ฉันต้องการเห็นข้อความ "หมดชั่วคราว" บนเมนูที่ปิดขาย เพื่อไม่เลือกรายการนั้น
- ในฐานะลูกค้า เมื่อส่งออเดอร์ไม่สำเร็จ (เน็ตหลุด/ระบบล่ม) ฉันต้องการเห็น error message ชัดเจนพร้อมปุ่มลองส่งใหม่ เพื่อไม่เข้าใจผิดว่าออเดอร์สำเร็จแล้วทั้งที่ยังไม่ถึงครัว

## Business Rules / เงื่อนไข
- **การแจ้งเตือนครัว/บาร์:** เมื่อลูกค้ายืนยันออเดอร์ (2-step confirm ตามสเปกเดิม) สำเร็จ ระบบพิมพ์สลิปออเดอร์ออกที่เครื่องพิมพ์ในครัว/บาร์ทันที สลิปต้องมีรายละเอียดอย่างน้อย: หมายเลขโต๊ะ, เวลา, รายการอาหาร/เครื่องดื่มที่สั่ง (ใช้การผูก QR กับหมายเลขโต๊ะตามสเปกเดิม เพื่อระบุปลายทาง/เนื้อหาสลิป)
- **สถานะออเดอร์:** ต้องมีอย่างน้อย 3 สถานะ:
  1. "ส่งแล้ว (รอครัวรับทราบ)" — ทันทีหลังลูกค้ายืนยันออเดอร์และสลิปพิมพ์ออก
  2. "ครัวรับทราบแล้ว (กำลังทำ)" — เมื่อพนักงานครัวกดรับทราบออเดอร์ (เช่น กดปุ่มที่ POS/เครื่องพิมพ์)
  3. "เสร็จ/เสิร์ฟแล้ว"
- **การแก้ไข/ยกเลิกออเดอร์โดยลูกค้า:** อนุญาตให้ลูกค้ายกเลิก/แก้ไขออเดอร์ได้ **เฉพาะขณะที่ออเดอร์ยังอยู่ในสถานะ "ส่งแล้ว (รอครัวรับทราบ)"** เท่านั้น เมื่อครัวกดรับทราบแล้ว (เปลี่ยนเป็น "ครัวรับทราบแล้ว") ออเดอร์จะถูกล็อก ลูกค้าไม่สามารถแก้ไข/ยกเลิกเองในระบบได้อีก — ถ้าลูกค้าต้องการเปลี่ยนแปลงหลังจากนั้นต้องเรียกพนักงานเป็นกรณีพิเศษ (exception path เท่านั้น ไม่ใช่ flow หลัก จึงไม่ขัดกับกติกาห้ามมีขั้นตอน "เรียกพนักงานรับออเดอร์" ใน user journey หลักตามโจทย์ 1)
- **การเปิด/ปิดขายเมนู:** พนักงานสามารถกดปิดขายเมนูรายการใดรายการหนึ่งแบบชั่วคราว (flag เปิด/ปิดสถานะขายรายเมนูแบบง่าย ไม่ใช่ real-time inventory count) เมื่อปิดขาย เมนูนั้นจะซ่อนหรือแสดงข้อความ "หมดชั่วคราว" ให้ลูกค้าเห็นทันทีเมื่อรีเฟรช/เปิดเมนูใหม่
- **การสั่งพร้อมกันหลายเครื่องที่โต๊ะเดียวกัน:** ออเดอร์จากทุกอุปกรณ์ที่สแกน QR เดียวกัน (โต๊ะเดียวกัน) จะถูกรวมเป็นตะกร้า/บิลเดียวกันของโต๊ะนั้น ไม่แยกเป็นคนละบิล (ดูสมมติฐานในหัวข้อ Open Questions)
- **Error handling เมื่อส่งออเดอร์ไม่สำเร็จ:** ถ้าส่งออเดอร์ไม่สำเร็จ (เน็ตหลุด/ระบบล่ม) ระบบต้องแสดง error message ชัดเจนให้ลูกค้าเห็นทันที พร้อมปุ่ม "ลองส่งใหม่" ห้ามแสดงว่าสำเร็จถ้ายังไม่ได้รับการยืนยันจาก backend จริง (ดูสมมติฐานในหัวข้อ Open Questions)
- **การ reset ตะกร้าเก่าของโต๊ะ:** ตะกร้า/session ของโต๊ะควรหมดอายุอัตโนมัติหลังออเดอร์ก่อนหน้าถูก mark ว่า "เสร็จ/เสิร์ฟแล้ว"/"ปิดบิลแล้ว" เพื่อไม่ให้ลูกค้ากลุ่มใหม่ที่มานั่งโต๊ะเดิมเห็นตะกร้าเก่า (ดูสมมติฐานในหัวข้อ Open Questions)

## ขอบเขต (Scope)
**อยู่ในขอบเขต (In scope):**
- กลไกพิมพ์สลิปแจ้งครัว/บาร์อัตโนมัติเมื่อลูกค้ายืนยันออเดอร์
- สถานะออเดอร์ 3 สถานะ: ส่งแล้ว (รอครัวรับทราบ) / ครัวรับทราบแล้ว (กำลังทำ) / เสร็จ-เสิร์ฟแล้ว
- การยกเลิก/แก้ไขออเดอร์โดยลูกค้าเอง เฉพาะก่อนที่ครัวจะกดรับทราบ
- ปุ่มเปิด/ปิดขายรายเมนูแบบง่าย (flag on/off) และการแสดงผล "หมดชั่วคราว" ฝั่งลูกค้า

**ไม่อยู่ในขอบเขต (Out of scope):**
- ระบบจัดการเมนู/สต๊อกแบบเต็มรูปแบบ (ราคา, เพิ่ม/ลบเมนู, นับสต๊อกจริงแบบ real-time) — ยังคงอยู่นอกขอบเขตตามที่ระบุไว้ใน [[01-spec/20260802-01-table-qr-self-order|20260802-01-table-qr-self-order]] ต้องทำเป็น requirement แยกในอนาคต
- ระบบชำระเงินออนไลน์/QR payment — ตามสเปกเดิม
- การแจ้งเตือนสถานะออเดอร์กลับไปยังลูกค้า (เช่น "อาหารกำลังทำ" / "เสิร์ฟแล้ว") — ตามสเปกเดิม ยังไม่รวมในเอกสารนี้
- รายละเอียดเชิงเทคนิคของเครื่องพิมพ์สลิป (ยี่ห้อ, โปรโตคอล เช่น ESC/POS ฯลฯ) — เป็นเรื่องของขั้นตอน design/technical (`02-design/02-technical`) ในเฟสถัดไป ไม่ใช่ของเอกสาร requirement นี้

## คำถามที่ยังไม่ชัดเจน (Open Questions)
- การสั่งพร้อมกันหลายเครื่องที่โต๊ะเดียวกัน — ผู้ใช้ไม่ได้ระบุ preference ชัดเจน ใช้สมมติฐานว่าออเดอร์จากทุกอุปกรณ์ที่สแกน QR เดียวกันจะถูกรวมเป็นตะกร้า/บิลเดียวกันของโต๊ะ ไม่แยกเป็นคนละบิล
- Error handling เมื่อส่งออเดอร์ไม่สำเร็จ — ใช้สมมติฐานว่าระบบต้องแสดง error message ชัดเจน พร้อมปุ่ม "ลองส่งใหม่" และห้ามแสดงว่าสำเร็จจนกว่า backend จะยืนยันจริง
- การ reset ตะกร้าเก่าของโต๊ะเมื่อลูกค้ากลุ่มใหม่มานั่งที่โต๊ะเดิม — ใช้สมมติฐานว่าตะกร้า/session ของโต๊ะจะหมดอายุอัตโนมัติหลังออเดอร์ก่อนหน้าถูก mark ว่า "เสร็จ/เสิร์ฟแล้ว"/"ปิดบิลแล้ว"
- รายละเอียดเชิงเทคนิคของเครื่องพิมพ์สลิป (ยี่ห้อ/โปรโตคอล ESC/POS ฯลฯ) ยังไม่ระบุ — เป็นเรื่องของขั้นตอน 02-design/02-technical ในเฟสถัดไป ไม่ใช่ของเอกสาร requirement นี้
